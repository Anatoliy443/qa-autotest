# Домашняя работа №4 — REST Assured

Задание: https://online.stepup.study/viewer/sessions/8167/tasks/4522

Решение выполнено по презентациям лекции и вебинара темы 4 и спецификации
запущенного `oa_at_train_project-1.0-SNAPSHOT.jar`.
Снимок Swagger сохранён в [homework4-openapi.json](homework4-openapi.json).

## Организация

- `RestApiBuilder` создаёт отдельный `RequestSpecification` с базовым URL,
  JSON Content-Type и Basic Auth для каждого запроса.
- `Urls` содержит пути эндпоинтов.
- `BaseApiTest` создаёт уникальные имена, запоминает ID и удаляет только товары,
  созданные текущим тестом, в `@AfterEach`, в том числе после падения ассерта.
- Для каждого эндпоинта выделен свой тестовый класс.
- REST Assured/Hamcrest и AssertJ проверяют статус и содержимое ответа;
  успешные изменения дополнительно проверяются чтением сохранённых данных.
- Все API-тесты отмечены тегом `api` (наследуется от базового класса).
  `apiTest` запускает только этот тег, последовательно и без пропуска по up-to-date.
- Вспомогательный код находится в `src/test/java`, поэтому библиотеки подключены
  через `testImplementation`; production-код предыдущих работ не зависит от них.

## Задача 1: четыре варианта GET /goods/list

Все четыре метода находятся в `GoodsListTest`:

| Требование | Метод |
| --- | --- |
| given / when / then, статус и пустой список | `emptyListUsingGivenWhenThen` |
| RequestSpecification, статус и пустой список | `emptyListUsingRequestSpecification` |
| Создание товара и встроенные проверки REST Assured | `createdGoodIsListedUsingRestAssured` |
| Создание товара и проверки AssertJ | `createdGoodIsListedUsingAssertJ` |

Пустое состояние этого API — HTTP 200 с JSON `{"goods":[]}`. Поэтому проверяется
пустота `goods`, а не пустая HTTP-строка: проверка пустой строки противоречила бы
фактическому формату учебного API. В двух других тестах проверяются размер списка,
ID, имя и цена созданного товара.

## Задача 2: матрица покрытия Swagger

| Операция | Коды Swagger без 500 | Класс / сценарии |
| --- | --- | --- |
| POST /goods/add | 200, 400 | `GoodsAddTest`: создание, дубликат имени, пустое/отсутствующее имя, пробелы, сломанный JSON, отрицательная и нулевая цена |
| GET /goods/{id} | 200, 404 | `GoodsGetTest`: существующий и отсутствующий товар |
| DELETE /goods/{id} | 200, 404 | `GoodsDeleteTest`: удаление с проверкой списка; отсутствующий товар |
| PATCH /goods/{id} | 200, 400, 404 | `GoodsPatchTest`: изменение полей, дубликат имени, отрицательная цена, обязательное имя, отсутствующий товар, изменение только имени |
| GET /goods/list | 200 | `GoodsListTest`: четыре варианта из лекции и пагинация |

Все 10 пар «операция + штатный код» покрыты проверками. 500 не используется
как ожидаемый код и не проверяется отдельным позитивным сценарием.
Схема `ProductRequest` требует `name` и для PATCH: запрос только с `price`
проверяется как 400. Противоречие этой схемы названию «частичное обновление»
не трактуется как доказанный дефект реализации.

## Запуск

Нужен JDK 17+; проверено на JDK 25. Если системная Java старая, задайте `JAVA_HOME`
на установленный новый JDK. Gradle используется через Wrapper из репозитория.

В первом терминале:

```shell
bash scripts/start-training-api.sh "$HOME/Downloads/oa_at_train_project-1.0-SNAPSHOT.jar.zip"
```

Скрипт распакует JAR в игнорируемую папку `build/training-api`, запустит сервер
на `127.0.0.1:8080` с отдельной H2-базой в памяти. Остановка — Ctrl+C.
При каждом запуске база пустая. Архив, JAR и пароль не добавляются в Git.

Swagger: http://127.0.0.1:8080/swagger-ui/index.html.
Для Basic Auth используйте учебные учётные данные из задания.

Во втором терминале:

```shell
read -s API_PASSWORD
export API_PASSWORD
./gradlew apiTest
```

После `read` введите учебный пароль и нажмите Enter. Имя по умолчанию — `admin`.
Параметры можно переопределить через `API_BASE_URL`, `API_USERNAME`, `API_PASSWORD`
или `-Dapi.baseUrl=...`, `-Dapi.username=...`, `-Dapi.password=...`.
Пароль рекомендуется передавать через окружение.

Тесты рассчитаны на отдельный пустой учебный экземпляр API: проверки пустого списка
и списка из одного товара не совместимы с чужими данными. Не запускайте одновременно
несколько наборов тестов и не добавляйте товары вручную во время прогона.
Тесты не очищают чужие товары и не зависят от порядка выполнения.

Отчёты:

- HTML: `build/reports/tests/apiTest/index.html`.
- JUnit XML: `build/test-results/apiTest/`.
- Предыдущая домашняя работа: `./gradlew test` или `./gradlew runAllTests`.

## BUG-01: GET отсутствующего товара возвращает 500 вместо 404

**Предусловие:** запущен учебный JAR, товар с ID `9223372036854775807` отсутствует.

**Шаги:** отправить авторизованный GET `/goods/9223372036854775807`.

**Ожидается:** HTTP 404 (Not found), как указано в Swagger для GET `/goods/{id}`.

**Фактически:** HTTP 500, тело:

```json
{"data":null,"message":"Internal server error"}
```

**Воспроизведение:**

```shell
curl -i -u "admin:$API_PASSWORD" \
  http://127.0.0.1:8080/goods/9223372036854775807
```

**Автотест:** `GoodsGetTest.missingGoodReturns404`.

**Сообщение ассерта:** `Expected status code <404> but was <500>`.

Дефект воспроизведён прямым HTTP-запросом и двумя прогонами тестов.
После исправления сервиса этот тест должен пройти без изменения ожидания.
